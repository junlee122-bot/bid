# BID SHIELD 아키텍처

이 문서는 2026-07-14 현재 저장소의 실제 구현을 설명합니다. 계획 기능은 “확장 경로”에서만 구분해 적습니다.

## 1. 설계 목표

1. **감사 가능한 계산**: 금액·위험·배분은 React나 LLM이 아니라 부수효과 없는 TypeScript 함수가 계산합니다.
2. **출처와 가정의 분리**: 조달 원천, 기업 재무 원천, 사용자 가정, 모델 파생값을 필드별 provenance로 구분합니다.
3. **불완전한 데이터의 명시**: 누락을 임의로 채우기보다 `null`, 품질점수, 경고, 합성 표시를 유지합니다.
4. **같은 입력의 같은 결과**: 기준 분석과 자금배분은 결정론적이며 Monte Carlo도 시드·표본 수·분포를 함께 보존합니다.
5. **실무 행동으로 연결**: 계약 분석에서 끝내지 않고 P90 자금 방어선, 배분 워터폴, 검토 큐, JSON·인쇄 보고서까지 연결합니다.
6. **비밀의 서버 격리**: 공공데이터포털 인증키는 Route Handler에서만 읽고 브라우저 번들·응답·오류에 넣지 않습니다.

## 2. 시스템 경계

```text
┌──────────────────────── 외부 원천 ────────────────────────┐
│ 나라장터 3종 공개 API                  기업 재무 CSV        │
└──────────────┬──────────────────────────┬───────────────────┘
               │ 서버 전용 인증키          │ 업로드·행별 검증
               ▼                           ▼
      /api/procurement/search          /api/import
               │                           │
               └────────────┬──────────────┘
                            ▼
              정규화 + 명시적 계약 가정 + provenance
                            │
                            ▼
                      ContractRecord
               ┌────────────┼──────────────┐
               ▼            ▼              ▼
          계약 분석     포트폴리오 분석   데이터 품질
               │            │              │
               ├──── Monte Carlo ──────────┤
               └──── 제한자금 배분 ────────┘
                            │
                            ▼
       화면 / 브라우저 localStorage / 근거 JSON / 인쇄
```

서버 DB는 없습니다. CSV Route Handler는 요청 메모리에서 검증한 뒤 결과를 반환하고 파일을 저장하지 않습니다. 결합된 `ContractRecord` 워크스페이스는 브라우저 `localStorage`의 `bid-shield.workspace.v1`에 최대 5,000건까지 저장합니다.

## 4. 핵심 데이터 계약

### 4.1 조달 정규화

`ProcurementRecord`는 공고·낙찰·계약과 공사·용역·물품의 서로 다른 응답을 공통 필드로 줄입니다. 알 수 없는 값은 `null`을 유지합니다.

- 식별·생애주기: `resource`, `kind`, 공고번호·차수, 계약번호
- 설명: 제목, 공고기관, 수요기관, 계약방법
- 시점: 공고·마감·개찰·계약일
- 금액: 추정·기초·낙찰금액, 낙찰률
- 연결 증거: 낙찰자, 원문 URL
- 원천표시: `koneps-live` 또는 `demo`, `isSynthetic`

### 4.2 구조화된 provenance

`ContractDataProvenance`는 세 부분으로 구성됩니다.

**기업**

- `stableKey`: 사업자번호 → 기업 ID → 정규화 기업명 순으로 선택한 원문을 FNV-1a로 가명화한 키
- `asOfDate`: 재무 기준일
- 연매출, 영업이익, 현금성자산, 유동자산·부채, 총부채, 수주잔고, 회수·지급일 스냅샷

원문 사업자등록번호는 결합 후 `ContractRecord`에 넣지 않습니다. `stableKey`는 그룹화용 비암호학적 가명이며 보안 해시나 익명화 보장을 뜻하지 않습니다.

**조달**

| 자원 | 생애주기 | 낙찰자 매칭 |
| --- | --- | --- |
| `notice` | `opportunity` | `not-applicable` |
| `award` | `awarded` | 기업명과 낙찰자 보수 비교 |
| `contract` | `contracted` | 기업명과 낙찰자 보수 비교 |

매칭은 NFKC, 공백·구두점, 일반적인 법인 표기를 제거한 뒤 완전일치만 인정합니다. 다른 상호를 임의로 같은 기업으로 추정하지 않습니다. 결과는 `matched`, `mismatch`, `unknown`, `not-applicable` 중 하나입니다.

**필드 근거**

각 핵심 필드는 `origin`(`procurement`, `company-financial-csv`, `user-input`, `model`)과 `evidence`(`source`, `user-assumption`, `model-derived`)를 갖습니다. 설명과 기준일을 붙여 “숫자가 어디서 왔는가”를 JSON으로 재구성할 수 있습니다.

## 5. 데이터 품질 계산

`assessWorkspaceDataQuality(contracts, asOfDate)`는 시스템 시계를 직접 읽지 않는 순수 함수입니다.

### 완전성

계약별로 다음 범주의 존재 여부를 확인한 뒤 충족률을 0~100으로 반올림합니다.

- 기업키·기업 원천·재무 기준일
- 9개 재무 스냅샷 필드
- 조달 자원·업무·원천·생애주기·원문 URL·낙찰자 매칭
- 계약금액, 원가율·원가, 가용현금, 유동자산·부채, 지급지연의 필드 provenance
- 공고 이후 단계에는 낙찰자와 `unknown`이 아닌 매칭 결과 추가

provenance가 없는 이전 형식 계약은 완전성 0점과 오류를 받습니다. 합성 계약의 완전성은 최대 35점입니다.

### 최신성

```text
최신성 = clamp(100 - 재무 경과일 / 365 × 100, 0, 100)
```

기준일이 없으면 0점, 평가일보다 미래면 경고 후 경과일을 0으로 둡니다. 365일 초과는 경고합니다. 합성 계약은 최대 20점입니다. 워크스페이스 완전성·최신성은 계약별 점수의 산술평균이며, 데이터 허브 표시점수는 `완전성×0.65 + 최신성×0.35`입니다.

`sourceCount`는 워크스페이스에 나타난 기업 원천과 조달 원천 문자열의 서로 다른 개수입니다. 낙찰자 불일치는 오류, 미확인은 경고입니다.

## 6. 분석 파이프라인

### 6.1 기준 계약 분석

`analyzeContract`는 입력을 정규화한 뒤 다음 순서로 계산합니다.

1. 물량 변화로 계약매출과 변동원가를 조정합니다.
2. 고정원가·변동원가에 원가 충격을 반영합니다.
3. 선금, 월/단계/준공 지급, 지급지연, 유보금, 보증예치를 월에 배치합니다.
4. 프로젝트 원가와 기업 운영비·기존 원리금·차입이자를 분리해 12개월 현금흐름을 만듭니다.
5. 최저현금, 최대 현금부족, 런웨이, 미회수채권, 12개월 이후 잔여계약가치를 계산합니다.
6. 금융비용을 근사한 생존마진과 손익분기 원가충격을 계산합니다.
7. 여섯 위험 기여도를 합하고 금융구조를 제안합니다.

계약 직접원가와 기업 전체 운영비·기존 채무는 중복 합산하지 않도록 별도 필드입니다.

### 6.2 기업 재무 신호

provenance 재무 스냅샷이 있을 때만 다음을 계산합니다.

```text
유동비율(%)       = 유동자산 / 유동부채 × 100
순운전자본        = 유동자산 - 유동부채
부채/매출(%)      = 총부채 / 연매출 × 100
수주잔고/매출(%)  = 수주잔고 / 연매출 × 100
```

분모가 0이거나 수주잔고가 없으면 해당 비율은 `null`입니다. 유동비율·부채/매출·수주잔고/매출은 부채 상환부담 10점 안에서 최대 2.5점을 구성합니다. 유동비율 100% 미만, 수주잔고/매출 100% 초과는 별도 경고를 만듭니다. 순운전자본과 평균 회수·지급일은 현재 표시·검토용입니다.

### 6.3 기업키별 포트폴리오

같은 기업 재무가 계약마다 반복 저장되므로 단순 합계하지 않습니다.

1. `stableKey`가 있으면 사용하고, 이전 형식은 정규화 기업명, 기업명도 없으면 계약별 임시키를 사용합니다.
2. 같은 기업에서 시작현금이 충돌하면 **최솟값**, 월 운영비+채무상환+기존차입이자는 **최댓값**을 사용합니다.
3. 계약별 프로젝트 유입·원가·보증 이동은 합산하되 기업 고정유출은 월마다 한 번만 차감합니다.
4. 기업 유동성 버퍼는 `max(월 기업 고정유출, 그룹 예상원가 합계×3%)`입니다.
5. 기업 필요자금은 `max(0, 버퍼−12개월 최저현금)`이며 포트폴리오 값은 기업별 합계입니다.

계약별로 독립 계산한 필요자금 합계는 `conservativeContractFundingRequirementKrw`에 **보수 상한**으로 보존합니다. 의사결정실의 가용예산 비율과 계약별 워터폴은 이 상한을 기준으로 합니다.

## 7. Monte Carlo 엔진

`simulateContractRisk`는 기존 계약 분석기에 시나리오를 반복 전달하는 감사 가능한 스트레스 래퍼입니다.

### 재현성과 경계

- 엔진 버전: `1.0.0`
- 기본 표본: 500회
- 요청 표본 수: 반올림 후 100~1,000회로 제한
- 기본 시드: `0x42494453`; 문자열은 FNV-1a로 32비트 해시
- 불확실성 배수: 0~3으로 제한
- 난수: Mulberry32, 표준정규: Box–Muller
- 분위수: 정렬 표본의 선형보간

### 기본 분포와 상관 구조

| 변수 | 평균 | 표준편차 | 표본 경계 | 공통요인 loading |
| --- | ---: | ---: | ---: | ---: |
| 원가상승 | 5% | 7% | -10~35% | 0.45 |
| 추가 지급지연 | 20일 | 30일 | -30~180일 | 0.35 |
| 금리변화 | 0.75%p | 1.5%p | -3~7%p | 0.55 |
| 물량변화 | -2.5% | 10% | -35~20% | -0.25 |

각 변수의 표준정규 충격은 다음과 같습니다.

```text
z_driver = loading × z_systemic + sqrt(1-loading²) × z_independent
sample   = clamp(mean + sd × z_driver, minimum, maximum)
```

이는 불리한 공통 상황에서 원가·지연·금리가 함께 오르고 물량이 줄어드는 **명시적 가정**이지, 관측 데이터로 추정한 인과·공분산 구조가 아닙니다.

### 출력

- 현금부족, 음수 생존마진, 고위험·임계 표본의 비율
- 필요자금, 최대 현금부족, 생존마진, 위험점수의 min/P10/P25/P50/P75/P90/P95/max/mean
- 위험등급 분포와 충격 변수 표본 분위수
- 각 변수와 생존마진·필요자금의 표본 Pearson 상관
- 최악 표본: 위험점수 최대 → 필요자금 최대 → 생존마진 최소 → 표본번호 순
- 엔진 버전, 실제·요청 표본 수, 시드, 배수, 분포, 한계

P90은 이 가정분포 아래 표본의 90백분위입니다. 실제 지급지연·부도 빈도로 보정된 예측확률이 아닙니다. 의사결정실은 성능을 위해 기준 위험·필요자금 상위 최대 24건만 Monte Carlo에 넣고, 전체 계약은 기준 포트폴리오·배분에 유지합니다.

## 8. 제한 자금배분 엔진

`allocateWorkingCapital`은 정렬된 계약에 예산을 순차 배분합니다. 기본 정책은 `viable-only`입니다.

### 적격성

- 필요자금이 0이면 `not-required`
- 필요자금이 있고 생존마진이 음수이면 자동 배분 보류(`manual-review-hold`)
- 나머지는 자동 배분 적격
- 사용자가 `include-manual-review`를 명시하면 보류 계약도 포함하지만 경고를 유지

### 우선순위

```text
우선순위 =
  위험 긴급도 × 0.35
  + 유동성 강도 × 0.25
  + 런웨이 긴급도 × 0.25
  + 생존마진 경제성 × 0.15
```

- 위험 긴급도: 위험점수 0~100
- 유동성 강도: `필요자금/조정매출`, 35%에서 100점
- 런웨이 긴급도: `(1-런웨이/12)×100`
- 생존마진 경제성: -5%에서 0점, 15%에서 100점

동점은 위험점수 내림차순, 런웨이 오름차순, 필요자금 내림차순, 계약 ID·조달번호·계약명·기업명 사전순입니다. 배분액은 원 단위로 반올림하며 예산을 초과하지 않습니다. 마지막 적격 계약은 부분 배분될 수 있고, 미배분 사유 코드를 함께 반환합니다.

“우선순위 가중 완화율”은 회계금액이나 예상손실률이 아니라 `필요자금×(1+우선순위/100)`로 가중한 의사결정 지수입니다.

## 9. 의사결정실 산출물

`/decision`은 다음 입력을 즉시 재계산합니다.

- 예산: 계약별 보수 필요자금 상한의 0~150%
- 표본 수: UI 250·500·1,000회(엔진 경계는 100~1,000)
- 불확실성 배수: 0.8·1.0·1.35
- 손실계약 정책: 기본 보류 또는 명시 승인

화면은 P90 합계, 현금부족 표본비율, 위험분포, 필요자금 민감도, 배분 워터폴, 계약별 검토 큐, 원가×지급지연 매트릭스를 제공합니다.

**보고서 인쇄**는 `window.print()`와 인쇄 CSS를 사용합니다. **근거 JSON**은 다음을 포함합니다.

- 스키마 `bid-shield-decision-report/v1`, 생성시각
- 워크스페이스 출처·갱신시각·계약 수
- 데이터 품질 평가
- Monte Carlo 엔진 버전·표본 수·배수·시드 정책·해석 경고
- 예산·적격성 정책
- 입력 `ContractRecord`, 포트폴리오, 배분계획, 계약별 시뮬레이션 전체 결과

JSON에는 현재 브라우저의 분석 입력이 포함되므로 실제 기업정보를 다룰 때 보관·전송 권한을 확인해야 합니다.

## 10. 실패·보안 모델

- 상류 API 오류는 비밀·원본 URL을 제거한 정규화 오류로 반환합니다.
- `fallback=true`는 실패 범위만 합성값으로 채우고 `mixed/demo` 원천과 경고를 노출합니다.
- `fallback=false`는 키 누락 503, 잘못된 검색 400, 상류 장애 4xx/5xx로 실패를 숨기지 않습니다.
- CSV는 5MB·5,000행·셀 10,000자 제한, 수식 가능 문자열 경고, 사업자번호·중복·범위 검증을 적용합니다.
- 로컬 저장 실패는 메모리 분석을 중단하지 않지만 지속성은 보장하지 않습니다.

현재 구현하지 않은 운영 통제:

- 사용자 인증·조직 권한·행 수준 권한
- 서버 DB, 암호화 저장, 보존·삭제·백업
- 서버 감사로그, 승인 워크플로, 전자서명
- 요청자별 속도 제한, 상류 재시도·회로차단

실데이터 운영 전에 반드시 보강해야 합니다.

## 11. 테스트 불변식

`pnpm check`은 lint → typecheck → test → production build를 실행합니다. 분석 테스트는 특히 다음을 확인합니다.

- 같은 입력·시드의 같은 Monte Carlo 출력
- 표본 수 100~1,000 경계, 표본비율 0~100, 분위수 단조성
- 자금배분액 ≤ 예산, 배분액+미사용액=예산, 배분액+잔여공백=필요자금
- `viable-only`에서 음수 생존마진 계약 자동 배분 금지
- 동일 기업키의 현금·고정유출 중복 제거와 계약별 보수 상한 보존
- 기업 재무 신호 산식과 provenance가 없을 때의 호환성
- CSV 부분 오류, 별칭, 인코딩·템플릿과 나라장터 비밀 마스킹

## 12. 확장 경로

아래는 현재 구현이 아니라 KO-DLab 실데이터 확보 후의 순서입니다.

1. 계약·기업·월 시점 패널과 실제 지급·기성·원가·연체 outcome을 시간축으로 결합
2. 분포·상관·임계값을 학습/보정하고 시간·기업 단위 holdout으로 검증

5. 정책금융 상품별 한도·보증 규칙 플러그인과 실제 집행/성과 모니터링
