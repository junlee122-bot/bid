# BID SHIELD 2분 시연 대본

## 0. 시연 전 3분 점검

1. `pnpm dev` 또는 프로덕션 서버를 실행하고 `/api/health`가 200인지 확인합니다.
2. 브라우저에서 데이터 허브(`/data`)의 **데모로 초기화**를 실행해 모든 화면이 같은 출발점이 되게 합니다.
3. `/decision`을 한 번 열어 기본 500회 시뮬레이션 렌더링을 완료합니다.
4. 브라우저 확대 100%, 데스크톱 폭을 사용하고 알림·개인 북마크를 닫습니다.
5. 인터넷이나 나라장터 키가 없어도 데모가 되도록 **실시간 API를 발표 중 필수 경로로 사용하지 않습니다.**
6. 예비자료로 `/decision`의 **근거 JSON**과 **보고서 인쇄** 미리보기를 한 번 저장해 둡니다.

발표 시작 때 “화면 수치는 합성 데이터”임을 먼저 밝힙니다. 실제 데이터인 것처럼 연출하지 않습니다.

## 1. 클릭 경로 한눈에 보기

```text
포트폴리오(/)
  → 우선 검토 계약 1건
  → 계약 상세(/contracts/[id])
  → 기업 재무 건전성 + 12개월 현금흐름 + 위험 기여도
  → 좌측 의사결정실(/decision)
  → P90 필요자금 + 자금배분 워터폴 + 검토 큐

  → 손실계약 정책 기본 보류 확인
  → 근거 JSON
```

클릭 수를 줄이기 위해 `/decision` 탭을 별도 브라우저 탭에 미리 열어 두어도 됩니다.

## 2. 2분 발표 대본

### 0:00–0:15 — 문제

**화면:** 포트폴리오 `/`

**말:**

> 공공조달에서 수주는 매출이지만 현금은 아닙니다. 중소기업은 원가, 보증금, 인건비를 먼저 내고 대금은 나중에 받기 때문에, 흑자 계약도 중간에 현금이 끊길 수 있습니다. BID SHIELD는 ‘좋은 기업인가’가 아니라 ‘이 기업이 이 계약을 이 조건으로 버틸 수 있는가’를 계산합니다.

**포인터:** 총 계약금액보다 **기업키별 필요자금**, 위험 분포, 우선 검토 계약을 짚습니다.

### 0:15–0:38 — 데이터와 근거

**클릭:** 포트폴리오의 우선 검토 계약 한 건 → 계약 상세

**말:**

> 입력은 나라장터 공고·낙찰·계약과 기업 재무 CSV입니다. 이 계약에는 원천, 재무 기준일, 조달 생애주기, 낙찰자 일치 여부와 사용자 가정이 필드별로 남습니다. 그래서 원천 금액과 원가율·지급조건 같은 가정을 섞어 숨기지 않습니다.

**포인터:** 화면의 데이터 품질/근거 표시와 **기업 재무 건전성** 카드에서 유동비율·순운전자본·부채/매출·수주잔고/매출을 짚습니다.

### 0:38–0:58 — 계약 생존성

**화면:** 같은 계약 상세의 현금흐름·위험 기여도

**말:**

> 엔진은 선금, 유보금, 보증예치, 지급지연, 계약원가, 운영비와 기존 채무를 12개월로 펼칩니다. 여기서 최저현금과 최대 자금공백, 생존마진을 계산하고, 무엇이 위험점수를 만들었는지 기여도까지 설명합니다. 가정은 계약서와 원가명세에 맞게 수정하면 즉시 다시 계산됩니다.

**포인터:** 현금 잔액의 최저 구간, 생존마진, 가장 큰 위험 기여도 하나만 짚습니다. 모든 숫자를 읽지 않습니다.

### 0:58–1:25 — 확률형 하방

**클릭:** 좌측 **의사결정실** `/decision`

**말:**

> 단일 예상값의 착시를 줄이기 위해 원가, 지급지연, 금리, 물량을 계약별 고정 시드로 기본 500회 표본화합니다. P90 필요자금은 이 가정분포에서 표본의 90%가 넘지 않은 방어선입니다. 실제 부도확률이라고 과장하지 않고, 시드·분포·표본 수를 결과에 함께 남깁니다.

**포인터:** **P90 필요자금**, 현금부족 표본비율, 재현성 레지스트리, 위험 분포를 순서대로 짚습니다.

### 1:25–1:47 — 제한 자금배분

**화면:** 의사결정실의 자금배분 워터폴과 계약별 의사결정 큐

**말:**

> 금융기관이나 기업의 자금은 무한하지 않습니다. 위험 긴급도 35%, 유동성 강도 25%, 런웨이 25%, 생존마진 경제성 15%로 우선순위를 공개하고 예산이 끝날 때까지 배분합니다. 생존마진이 음수인 계약은 돈을 넣어 손실을 키우지 않도록 기본 자동배분에서 보류합니다.

**클릭:** 가용예산 슬라이더를 **70%에서 40%**로 내립니다.

**말:**

> 예산을 줄이면 같은 규칙으로 부분배분·미배분과 잔여 공백이 즉시 바뀌어 담당자의 다음 검토 큐가 만들어집니다.

### 1:47–2:00 — 실무 산출물과 결론

**클릭:** **근거 JSON**

**말:**

> 결과는 화면 캡처로 끝나지 않습니다. 입력 계약, 데이터 품질, 모델 버전, 시드, 분포, 포트폴리오, 배분 결과를 JSON으로 내보내고 인쇄 보고서도 만듭니다. BID SHIELD는 수주심사, 선금·지급조건 협상, 운전자금·보증 검토를 하나의 재현 가능한 의사결정 흐름으로 연결합니다.

## 3. 30초 압축 버전

> BID SHIELD는 나라장터와 기업 재무를 결합해 계약별 12개월 현금흐름과 생존마진을 계산합니다. 원가·지급지연·금리·물량을 고정 시드로 표본화해 P90 필요자금을 만들고, 제한 예산은 위험 35·유동성 25·런웨이 25·경제성 15의 공개 규칙으로 배분합니다. 음수 생존마진 계약은 자동 보류하며, 모든 원천·가정·품질·시드·배분은 JSON과 인쇄본으로 남깁니다. 현재 비율은 합성 가정의 표본비율이고, KO-DLab 실데이터 확보 후 시간 holdout과 P90 coverage로 보정할 계획입니다.

## 5. 예상 질의응답

### Q1. 기존 기업 신용조회와 무엇이 다릅니까?

기업 신용조회는 기업 전체의 과거 재무 상태를 중심으로 봅니다. BID SHIELD는 **특정 계약의 금액·원가·수행기간·지급·보증 조건**을 기업 현금·채무와 결합해 월별 공백을 계산합니다. 여기에 확률형 하방과 제한 예산 배분까지 연결한 것이 차이입니다.

### Q2. 왜 이 문제가 실제 금융기관에 필요합니까?

같은 기업도 선금 10%·월 지급 계약과 무선금·준공 지급 계약의 운전자금 위험이 다릅니다. 금융기관은 기업 한도 검토, 팩토링 대상 채권, 선금 요청, 보증 준비금을 계약 조건과 함께 볼 수 있고, 기업은 입찰 전 조건 협상과 수주 포트폴리오를 점검할 수 있습니다.

### Q3. 화면의 확률은 진짜 확률입니까?

아닙니다. 현재는 명시한 제한 정규분포를 고정 시드로 표본화한 **조건부 표본비율**입니다. 실제 부도·현금부족 빈도로 보정하지 않았습니다. 따라서 UI와 JSON 모두 예측확률이 아니라는 경고를 포함합니다.

### Q4. P90의 의미는 무엇입니까?

정렬한 필요자금 표본의 90백분위입니다. 현재 가정 아래 90% 표본이 이 금액 이하였다는 뜻입니다. 실제 90% coverage를 보장하지 않으며, KO-DLab 실제 자금공백으로 holdout coverage 85~95%를 확인해야 운영 P90로 승격합니다.

### Q5. Monte Carlo 분포와 상관은 어떻게 정했습니까?

현재 평균·표준편차·경계와 공통요인 loading은 보수적 시연 가정입니다. 원가·지연·금리가 같은 불리 상황에서 함께 오르고 물량이 줄 수 있는 방향만 표현합니다. 실데이터 확보 후 실제 잔차 분포·꼬리·상관을 train에서 적합하고 시간 holdout에서 검증합니다.

### Q6. AI/LLM은 어디에 썼습니까?

핵심 금액과 승인에 LLM을 쓰지 않았습니다. 금융 판단은 동일 입력에 동일 결과가 나고 식을 감사할 수 있어야 하므로 결정론적 현금흐름·확률형 스트레스·배분 엔진을 사용했습니다. 향후 LLM은 검증된 수치의 설명이나 근거 문서 검색에만 제한하고 숫자 생성·승인 권한은 주지 않을 계획입니다.

### Q7. 자금배분이 수학적 최적화입니까?

현재는 선형계획의 전역 최적해가 아니라, 공개된 35/25/25/15 점수로 정렬하는 결정론적 워터폴입니다. 장점은 담당자가 순위 이유와 동점 규칙을 바로 설명할 수 있다는 점입니다. 실제 성과 데이터가 생기면 같은 예산에서 실제 사건 포착과 자금공백 커버를 기준으로 챌린저 최적화와 비교합니다.

### Q8. 왜 손실 계약에 자금을 자동 배분하지 않습니까?

현금이 부족하다는 이유만으로 생존마진이 음수인 계약에 돈을 넣으면 손실을 확대할 수 있습니다. 기본 `viable-only`는 이를 수동검토 보류로 돌려 예산을 보존합니다. 법적 이행의무 등으로 꼭 투입해야 하면 사용자가 명시 승인 정책을 선택할 수 있고 경고가 남습니다.

### Q9. 같은 기업이 여러 계약을 가지면 현금이 중복되지 않습니까?

구조화된 안정 기업키로 묶어 기업 시작현금과 월 고정유출을 한 번만 반영합니다. 값이 충돌하면 낮은 현금과 높은 고정유출을 보수적으로 사용합니다. 포트폴리오 필요자금은 기업키별 계산의 합이고, 계약별 독립 계산 합계는 보수 상한으로 별도 보존합니다.

### Q10. 데이터 품질점수는 임의 숫자 아닙니까?

완전성은 코드에 정의된 provenance 필드 체크 충족률, 최신성은 재무 기준일 경과 0일 100점에서 365일 0점까지 선형 감소입니다. 데이터 허브 종합점수는 완전성 65%+최신성 35%이며 합성 데이터는 각각 35점·20점 상한을 둡니다. 낙찰자 불일치는 오류로 표시합니다.

### Q11. 나라장터와 기업은 어떻게 연결합니까?

현재 UI는 검증한 기업 한 건과 사용자가 선택한 조달 레코드 한 건을 명시적으로 결합합니다. 낙찰·계약 단계에는 낙찰자명을 보수적으로 정규화해 기업명과 완전일치 여부를 기록합니다. 자동 퍼지매칭으로 다른 기업을 억지로 연결하지 않습니다.

### Q12. 실제로 어떤 KODATA 데이터가 더 필요합니까?

가장 중요한 것은 기업키·계약키로 연결되는 실제 기성·청구·입금일, 계약 원가 발생·지급, 차입 상환일, 매출채권 aging, 계약변경·중단·보증사고입니다. 제공 여부는 KO-DLab 데이터 사전에서 확인해야 하며 현재 저장소는 있다고 주장하지 않습니다.

### Q13. 실데이터 검증은 어떻게 합니까?

기업·계약 단위 중복을 막고 과거 train, 중간 validation, 최신 동결 holdout으로 나눕니다. P90 coverage, pinball loss, PR-AUC, Brier, ECE, calibration slope, top-k lift를 평가하고 업종·규모별 안정성 및 롤링 백테스트를 수행합니다. 기준 미달이면 확률 표기를 하지 않고 시나리오 모드로 유지합니다.

### Q14. 개인정보·보안은 괜찮습니까?

인증키는 서버 전용이고 CSV 파일은 서버에 저장하지 않습니다. 결합 계약은 원문 사업자번호 대신 가명키를 씁니다. 다만 현재 워크스페이스는 브라우저 `localStorage`이고 인증·권한·암호화 DB·감사로그가 없으므로 공용 PC나 운영 민감정보 환경에 바로 쓰면 안 됩니다. 조직 배포 전에 해당 통제가 필요합니다.

### Q15. 결과를 감사할 수 있습니까?

의사결정실 JSON에 입력 계약, 필드 provenance, 데이터 품질, 모델 버전, 표본 수, 불확실성 배수, 시드 정책, 분포, 포트폴리오, 배분과 모든 시뮬레이션 결과가 들어갑니다. 같은 코드·입력·시드라면 결과를 재현할 수 있습니다.

### Q16. 구현 완성도를 어떻게 증명합니까?

데모 화면뿐 아니라 CSV 검증·나라장터 어댑터·계약 결합·12개월 분석·Monte Carlo·기업키 포트폴리오·자금배분이 실제 TypeScript 모듈로 분리되어 있습니다. `pnpm check`으로 lint, typecheck, 자동 테스트, production build를 한 번에 검증합니다.

### Q17. 5,000건에도 Monte Carlo를 모두 실행합니까?

아닙니다. 워크스페이스 저장 상한은 5,000건이지만 의사결정실의 대화형 Monte Carlo는 기준 위험·필요자금 상위 24건만 실행합니다. 기준 포트폴리오와 자금배분은 전체 계약을 사용합니다. 대규모 운영은 서버 배치·큐·버전 스냅샷으로 분리해야 합니다.

### Q18. 이 결과로 바로 대출해도 됩니까?

안 됩니다. 현재 모델은 의사결정 보조와 자료검증 도구입니다. 실제 대출·보증·투자는 최신 재무, 원가명세, 계약서, 상환계획, 기관 정책, 담당자 심사와 법적·규제 검토를 거쳐야 합니다.

## 6. 장애 시 백업 동선

### 실시간 API가 실패할 때

> 상류 API 장애를 숨기지 않고 합성 폴백과 경고로 구분하도록 설계했습니다. 오늘 시연은 재현성을 위해 합성 데이터로 진행하겠습니다.

데이터 허브 연결 시도를 반복하지 말고 기존 합성 워크스페이스로 돌아갑니다.

### 의사결정실 렌더링이 늦을 때

표본 수를 250회로 낮추고:

> 엔진은 100~1,000회 경계 안에서 같은 시드로 재현되며, 발표 속도를 위해 250회로 낮추겠습니다.

라고 설명합니다.

### 다운로드가 막힐 때

**보고서 인쇄** 미리보기 또는 미리 저장한 JSON을 보여주고, JSON의 `model`, `dataQuality`, `allocationPlan`, `simulations` 키만 짚습니다.
