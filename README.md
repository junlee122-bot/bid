# BID SHIELD

**수주가 매출이 되는 순간이 아니라, 현금이 버티는지를 계약 전에 판단합니다.**

BID SHIELD는 나라장터 공고·낙찰·계약 데이터와 기업 재무 CSV를 결합해 공공조달 계약의 12개월 현금흐름, 생존마진, 자금 공백과 안전 금융구조를 계산하는 의사결정 앱입니다. 단순 기업 조회가 아니라 “이 기업이 이 계약을 이 조건으로 수행할 때 언제 얼마의 현금이 부족하며, 제한된 운전자금을 어디에 먼저 배분해야 하는가”를 설명 가능한 숫자로 답합니다.

> 저장소의 기본 워크스페이스는 실제 기업·기관·계약과 무관한 합성 데모입니다. 현재 모델은 규칙 기반 스트레스 도구이며, 화면의 표본비율은 실제 부도확률이나 대출 승인확률이 아닙니다.

## 핵심 차별점

- **계약 단위 생존성 분석**: 계약원가, 선금, 유보금, 보증예치, 지급지연, 기존 채무와 운영비를 월별 현금흐름으로 연결합니다.
- **기업 재무와 계약조건의 결합**: 유동비율, 순운전자본, 부채/매출, 수주잔고/매출 신호를 계약 위험에 함께 반영합니다.
- **확률형 스트레스**: 원가·지급지연·금리·물량 충격을 고정 시드로 반복 표본화하여 현금부족 표본비율과 P90 필요자금을 제시합니다.
- **제한 예산 배분**: 위험 긴급도 35%, 유동성 강도 25%, 현금 런웨이 25%, 생존마진 경제성 15%의 공개 규칙으로 자금 우선순위를 만듭니다.
- **근거 추적**: 조달 원천, 기업 재무 기준일, 사용자 가정, 모델 파생값, 조달 생애주기와 낙찰자 일치 여부를 구조화해 보존합니다.
- **재현 가능한 산출물**: 의사결정실에서 인쇄용 보고서와 입력·모델 설정·품질·배분·시뮬레이션을 포함한 JSON을 내보냅니다.

## 화면 구성

| 경로 | 역할 |
| --- | --- |
| `/` | 계약 규모, 위험 분포, 기업키별 필요자금, 집중도와 우선 조치를 요약 |
| `/contracts` | 계약 검색·필터·정렬과 데이터 품질 확인 |
| `/contracts/[id]` | 12개월 현금흐름, 위험 기여도, 기업 재무 신호, 금융구조, 기준 가정 편집 |
| `/scenario` | 원가·지급지연·금리·물량 스트레스의 기준 대비 변화 비교 |
| `/decision` | 확률형 스트레스, P90 방어선, 제한 예산 배분, 검토 큐, 2축 스트레스 매트릭스 |

| `/methodology` | 계산식, 가정, 위험점수와 한계 |

## 빠른 시작

요구사항은 **Node.js 24 이상**과 **pnpm 11.7.0**입니다.

```bash
pnpm install --frozen-lockfile
pnpm dev
```

`http://localhost:3000`을 엽니다. 환경변수가 없어도 합성 데모로 전체 분석 흐름을 실행할 수 있습니다.

실시간 나라장터 조회를 사용하려면 `.env.example`을 `.env.local`로 복사하고 공공데이터포털 인증키를 입력합니다.

```dotenv
KONEPS_SERVICE_KEY=공공데이터포털_일반인증키
KONEPS_API_TIMEOUT_MS=8000
```

- 인증키는 서버에서만 읽습니다. `NEXT_PUBLIC_` 접두사를 붙이지 마세요.
- 범위별 제한시간은 기본 8,000ms이며 500~30,000ms로 제한됩니다.
- 실시간 조회가 실패하고 `fallback=true`이면 실패 범위만 합성 데이터로 대체되므로 응답의 `source`, `isSynthetic`, `warnings`를 확인해야 합니다.

연결 대상은 공공데이터포털의 [나라장터 입찰공고정보서비스](https://www.data.go.kr/data/15129394/openapi.do), [낙찰정보서비스](https://www.data.go.kr/data/15129397/openapi.do), [계약정보서비스](https://www.data.go.kr/data/15129427/openapi.do)입니다. 오퍼레이션, 팬아웃, 오류·폴백 규칙은 [데이터 연동 문서](docs/DATA_INTEGRATION.md)에 정리했습니다.

## 실제 데이터 사용 흐름

1. `/data`에서 CSV 템플릿을 내려받아 기업 재무정보를 원(KRW) 단위로 입력합니다.
2. 업로드 결과의 행별 오류·경고와 accepted/rejected 건수를 확인합니다.
3. 나라장터에서 자원(공고·낙찰·계약), 업무(공사·용역·물품), 기간과 키워드를 지정해 조회합니다.
4. 금액이 있는 조달 레코드와 검증된 기업 한 건을 선택합니다.
5. 공개 데이터에 없는 원가율·운영비·상환액·수행기간·지급·보증 조건을 명시적으로 확인합니다.
6. 생성된 계약 상세에서 원가명세, 계약서, 자금계획과 대조해 기준 가정을 수정합니다.
7. `/decision`에서 예산·표본 수·불확실성·손실계약 배분정책을 바꿔 검토 큐를 만들고 JSON 또는 인쇄본을 보존합니다.

CSV 업로드만으로 계약은 생성되지 않습니다. **기업 레코드 한 건과 조달 레코드 한 건을 결합**해야 합니다. 브라우저 워크스페이스는 서버 DB가 아니라 `localStorage`에 최대 5,000건까지 저장되므로 공용 PC에서는 실제 기업 데이터를 사용하지 마세요.

## 기업 CSV

필수 열은 다음 7개입니다.

```text
company_name,annual_revenue,operating_profit,cash_and_equivalents,current_assets,current_liabilities,total_debt
```

선택 열은 `company_id`, `business_registration_no`, `industry_code`, `credit_grade`, `existing_order_backlog`, `average_collection_days`, `average_payment_days`, `employee_count`, `as_of_date`입니다. UTF-8과 CP949/EUC-KR, 최대 5MB·5,000행을 지원합니다.

각 필드가 현재 모델에서 어디에 쓰이고 KO-DLab 실데이터로 무엇을 확장할지는 [KODATA 필드 맵](docs/KODATA_FIELD_MAP.md)을 확인하세요.

## 분석 엔진

### 계약 현금흐름

분석기는 계약 수행기간을 최대 12개 월 구간으로 전개합니다.

- 조정 매출 = 계약금액 × 물량 변화
- 조정 원가 = 고정원가 + 물량연동 변동원가에 원가 충격 적용
- 생존마진 = 조정 매출 − 조정 원가 − 추정 금융비용
- 필요자금 = max(0, 유동성 버퍼 − 12개월 최저 예상현금)
- 위험점수 = 마진, 유동성, 지급지연, 부채부담, 낙찰할인, 실행조건 기여도의 합

선금은 1개월 차 유입, 보증예치는 1개월 차 유출 후 계약·지연기간 종료 다음 달 반환으로 배치합니다. 유보금은 준공 대금 지급 1개월 뒤 회수하는 것으로 가정합니다. 12개월 이후 잔여 계약대금과 12개월 안에 기성되었지만 아직 회수하지 못한 채권은 구분합니다.

### 기업 재무 신호

구조화된 기업 재무 provenance가 있을 때 다음 신호를 파생합니다.

- 유동비율 = 유동자산 ÷ 유동부채
- 순운전자본 = 유동자산 − 유동부채
- 부채/매출 = 총부채 ÷ 연매출
- 수주잔고/매출 = 기존 수주잔고 ÷ 연매출

유동비율·부채/매출·수주잔고/매출은 부채 상환부담 기여도 안에서 최대 2.5점을 사용합니다. 순운전자본은 표시·검토 신호이며 현재 위험점수에 별도 가점을 더하지 않습니다.

### 포트폴리오 필요자금

동일 기업의 여러 계약은 구조화된 `stableKey`로 묶습니다. 기업별 시작현금은 충돌 값 중 낮은 값, 월 고정유출은 높은 값을 한 번만 사용합니다. 기업별 12개월 최저현금과 `max(월 고정유출, 합산 예상원가의 3%)` 버퍼 차이를 필요자금으로 계산하고 이를 합산합니다. 계약을 서로 독립으로 본 필요자금 합계는 **보수 상한**으로 별도 표시합니다.

### Monte Carlo 스트레스

- 기본 500회, 허용 범위 100~1,000회
- 기본 시드 `0x42494453`; 의사결정실은 `BID-SHIELD-2026:{contractId}` 문자열 시드를 해시해 계약별로 고정
- Mulberry32 난수와 Box–Muller 표준정규 표본
- 공통 불리 요인과 변수별 독립 충격을 결합한 제한 정규분포
- 기본 평균/표준편차/경계: 원가 `5/7/-10~35%`, 지급지연 `20/30/-30~180일`, 금리 `0.75/1.5/-3~7%p`, 물량 `-2.5/10/-35~20%`
- 공통요인 loading: 원가 0.45, 지연 0.35, 금리 0.55, 물량 -0.25

현금부족 표본비율은 “표본 중 최대 현금부족이 0보다 큰 비율”입니다. P90 필요자금은 명시한 분포에서 필요자금 표본의 90백분위이며, 실제 사건 빈도로 보정된 예측확률이나 손실 VaR가 아닙니다. 검증 계획은 [모델 검증 문서](docs/MODEL_VALIDATION.md)에 있습니다.

### 제한 자금 배분

기본 `viable-only` 정책은 필요자금이 있어도 **생존마진이 음수인 계약을 자동 배분에서 보류**합니다. 적격 계약은 아래 점수로 정렬한 뒤 예산이 소진될 때까지 폭포식으로 배분합니다.

| 구성 | 가중치 | 현재 산식 |
| --- | ---: | --- |
| 위험 긴급도 | 35% | 0~100 위험점수 |
| 유동성 강도 | 25% | 필요자금/조정매출, 35%에서 만점 |
| 런웨이 긴급도 | 25% | 12개월에서 0점, 0개월에서 100점 |
| 생존마진 경제성 | 15% | -5%에서 0점, 15%에서 만점 |

마지막 계약은 부분 배분될 수 있습니다. 동점은 위험점수, 짧은 런웨이, 큰 필요자금, 식별자 사전순으로 결정합니다. 사용자가 `include-manual-review`를 명시하면 손실 예상 계약도 포함할 수 있지만, 결과는 수동 검토 경고를 유지합니다.

## 데이터 품질과 근거 추적

결합 계약은 다음을 구조화해 보존합니다.

- 기업: 원문 식별자 대신 비암호학적 가명 `stableKey`, 재무 기준일, 재무 스냅샷
- 조달: `notice → opportunity`, `award → awarded`, `contract → contracted` 생애주기, 원문 URL, 낙찰자, 기업명 일치 상태
- 필드: `source`, `user-assumption`, `model-derived` 증거 유형과 출처·설명·기준일
- 경고: 재무 기준일·수주잔고·회수일 누락, 합성 데이터, 낙찰자 불일치 등

데이터 허브의 실제 품질점수는 **완전성 65% + 최신성 35%**입니다. 완전성은 코드에 정의된 provenance 체크 충족률이고, 최신성은 평가일 기준 재무정보 경과일이 0일이면 100점에서 365일에 0점으로 선형 감소합니다. 합성 데이터는 완전성 35점·최신성 20점으로 상한을 둡니다. 낙찰자 불일치는 오류, 미확인은 경고로 반환합니다.

## 내부 API

```http
GET /api/procurement/search?resource=all&kind=all&keyword=데이터&from=2026-07-01&to=2026-07-13&page=1&pageSize=20&fallback=true
```

`resource=all&kind=all`은 최대 9개 상류 요청을 병렬 수행합니다. 엄격한 실시간 연결 확인에는 `fallback=false`를 사용하세요.

```bash
# CSV 템플릿
curl --fail --output company-template.csv http://localhost:3000/api/import

# CSV 스키마
curl --fail http://localhost:3000/api/import?format=json

# 서버 상태
curl --fail http://localhost:3000/api/health
```

## 검증

```bash
pnpm check
```

`pnpm check`은 ESLint, TypeScript 검사, Node 내장 테스트, 프로덕션 빌드를 순서대로 실행합니다. 자동 테스트는 현금흐름·포트폴리오·금융구조·Monte Carlo 재현성·표본 경계·자금배분 보존식·기업 재무 신호·CSV·나라장터 정규화와 비밀 마스킹을 포함합니다.

## 한계와 운영 주의

- 조달금액은 실제 현금 입금액·입금일이 아닙니다. 부가가치세, 변경계약, 기성·검수·입금이력을 원문과 대조해야 합니다.
- 브라우저 로컬 저장만 제공하며 조직 인증, 권한, 서버 감사로그, 암호화 저장, 백업은 구현하지 않았습니다.
- 현 모델은 12개월 계획용 추정치로 대출 심사, 투자 권유, 부도 예측 또는 법률 판단을 제공하지 않습니다.
- 의사결정실의 상위 24건만 화면 응답성을 위해 Monte Carlo를 실행하지만 기준 자금배분은 전체 계약을 사용합니다.
- 운영 적용 전 최신 재무제표, 계약 원가명세, 지급·보증 조항, 상환일정과 담당자 승인이 필요합니다.

## 기술 스택

- Next.js 16 App Router, React 19.2, TypeScript
- Tailwind CSS 4, Geist
- 의존성 없는 TypeScript 분석·CSV 엔진과 SVG 차트
- Node 내장 테스트, ESLint, GitHub Actions
